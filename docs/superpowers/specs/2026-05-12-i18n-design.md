# Multi-language support (i18n)

**Date:** 2026-05-12
**Repo:** kukui-studio
**Status:** Spec — not yet approved.

## Why

Kukui Studio is targeted at online educators worldwide, but every UI string is currently inline English. Two distinct translation surfaces need to be considered:

1. **Studio chrome** (sidebar, header, form labels, buttons, errors) — translated for the *author* using the tool.
2. **Activity runtime UI** (the chrome inside each activity component: "Submit", "Try again", "Card 1 of 2", "Reveal letter") — translated for the *learner* running the activity inside an LMS.

Author-facing content (an activity's title, prompt, card front/back text) is **not** in scope — those are authored by the educator and live inside the activity's JSON config. If an author wants a Spanish flashcard, they type Spanish into the form.

## Audience-driven decisions

### Which languages to launch with?

Recommended launch set: **English (current default), Spanish, Brazilian Portuguese**. Three languages cover the bulk of online-learning markets we're realistically reaching, are translatable with quality LLM drafts + native review, and exercise the framework without ballooning the maintenance burden.

Hold for phase 2: Hawaiian (cultural significance for the project's UH JABSOM origins; small string count makes this cheap once the framework exists), Mandarin, Japanese, French, German, Arabic (forces the RTL pass).

### How does the user pick a language?

Three options:

- **A.** Browser language only (`navigator.languages`), no UI toggle. Auto-detect, no per-user preference.
- **B.** Auto-detect on first visit, override via a header dropdown, persist to localStorage.
- **C.** URL segment (`/es/`, `/pt-BR/`) plus a toggle. SEO-friendly, shareable, but adds routing complexity.

**Recommendation: B.** Best default behavior, easy override, persists across sessions. SEO benefit of C isn't load-bearing for an authoring tool — most pages aren't indexed anyway.

## Stack decisions

### Library

**Recommended: react-i18next** (paired with i18next).

- Industry standard for React, well-maintained
- Hooks-based: `const { t } = useTranslation(); t("key")`
- Built-in plural rules (`t("card", { count: 2 })` → "2 cards"), nested keys, namespace support
- ~30KB gzipped for core + react binding
- Format.js (`<FormattedMessage>`) is the main alternative; equally good but heavier and component-based instead of hook-based

### Translation file format

**One JSON per locale, namespaced by app section.** Structure:

```
apps/studio-app/src/locales/
├── en/
│   ├── common.json        // shared UI strings (Save, Cancel, errors)
│   ├── sidebar.json       // Bloom labels, activity names
│   ├── header.json
│   └── docs-nav.json
└── es/
    └── …same shape

packages/core/src/locales/
├── en/
│   ├── flashcards.json
│   ├── crossword.json
│   └── …one per activity
└── es/
    └── …same shape
```

Activity components import their own namespace so they're self-contained for SCORM packaging.

### Locale detection

```ts
i18n
  .use(LanguageDetector)
  .init({
    fallbackLng: "en",
    supportedLngs: ["en", "es", "pt-BR"],
    detection: { order: ["localStorage", "navigator"], caches: ["localStorage"] },
  });
```

## Affected surfaces

### Studio chrome (~250 strings)

Files to extract from:
- `App.tsx` — sidebar group labels, validation badge, button labels, toolbar labels, footer copy
- `EditorForm.tsx` — RJSF strings (Add, Remove, Move up, Move down)
- `AIEditor.tsx` — AI Assist prompts, error messages, placeholders
- Form widgets — File upload labels, validation messages, etc.

### Activity runtime UI (~300 strings total across 24 activities)

Each `packages/core/src/components/<kind>/<Kind>.tsx` has ~10–30 inline strings. Extraction is mechanical but high-volume.

### Docs and blog

**Out of scope for this phase.** Markdown content is content, not chrome. If we want Spanish docs, we add `content/docs/es/getting-started.md` alongside `content/docs/getting-started.md` and switch by locale. Defer to a separate effort.

### Activity content (authored JSON)

**Out of scope.** Each `cards[].front`, `prompt`, `title` is what the educator types. We give them a Studio in their language; they author in whatever language they want. Maybe later we add a "duplicate this activity for another language" workflow, but that's a feature, not i18n.

## Phasing

1. **Phase 1 (framework, this spec):** Install react-i18next, set up detector + persistence + language toggle in header. Extract Studio chrome to `en/*.json`. Add Spanish + Brazilian Portuguese translations (LLM-drafted, native-reviewed). Activity components stay English.
2. **Phase 2:** Extract activity runtime strings, translate. Adds proper internationalization for what learners see.
3. **Phase 3 (optional):** Docs/blog content, RTL support (Arabic / Hebrew), more languages.

## Non-goals

- No CMS or external translation management platform — JSON files in the repo, PRs for updates.
- No automatic machine translation at runtime. Translations are static, reviewed, shipped.
- No translation of author-supplied content. The educator types in whatever language they want; the runtime UI around it is what we translate.
- No locale-specific dates/numbers beyond what `Intl` already gives us.

## Open questions

1. Confirm the launch language set — English + Spanish + Brazilian Portuguese, or different?
2. Should the toggle live in the header (always visible) or in a settings dialog (out of the way)?
3. SCORM-packaged activities ship one bundle per kind — should each bundle ship all locales (small zip increase) or just the locale the author picked at download time?
4. How aggressively should we machine-translate vs require human review before shipping? My default: ship machine-drafts behind a `quality: "draft"` flag in the JSON, mark them in the UI ("automatic translation"), promote to no-flag after native review.

## Cost estimate

- **Phase 1 framework + 3 languages:** 2–3 days of dev work + native review on Spanish/Portuguese
- **Phase 2 activity strings:** 3–4 days (mechanical extraction across 24 components + translation)
- **Maintenance:** ~1 hour per new feature with strings, ongoing
